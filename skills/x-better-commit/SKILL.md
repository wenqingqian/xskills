# Better Commit Messages

Produce commit messages a reviewer can trust: a title that survives
`git log --oneline` scanning and a body that carries the why. The rules
below govern both halves of every message this skill writes.

## When to Use

- **On explicit invocation**: draft a message for staged/uncommitted work
  and commit; rewrite the last commit's message; or print an improved
  message for an existing commit without touching history.
- **Skip**: throwaway WIP snapshots the user explicitly wants committed
  fast; merge commits and rebase artifacts generated by tooling.

## Modes

| Invocation | Action |
| --- | --- |
| `x-better-commit` | Draft from staged changes (fall back to unstaged), then commit |
| `x-better-commit --amend` | Rewrite the last commit message; only if unpushed |
| `x-better-commit <rev>` | Print an improved message for `<rev>`; never rewrite history |

## Workflow

```
1: gather   git status --porcelain; git diff --cached (fall back to
            git diff); git show <rev> for a rewrite; git log --oneline
            -10 to learn the repo's own type vocabulary
2: draft    title per Title Rules, body per Body Rules
3: check    run the Final Check below; split mixed commits first
4: apply    new commit via git commit with a heredoc message; amend only
            when the branch has no upstream or the commit is unpushed
            (git log @{u}..HEAD)
```

## Title Rules

1. **Format** — `<type>: <summary>`, or `<type>(<scope>): <summary>` when
   the repo's log uses scopes. Types: `feat fix refactor docs test chore
   perf build ci style`; follow the repo's existing vocabulary when it
   differs.
2. **Imperative mood** — "add", not "added" or "adds". Lowercase summary,
   no trailing period.
3. **Length** — summary <=50 chars soft target, 72 hard limit.
4. **Specific and diff-grounded** — name the actual change and its effect
   ("fix crash when config path is unset", not "fix bug", "update files",
   "minor changes"). Every word must be backed by the diff.
5. **One coherent purpose** — a tightly coupled change set (the feature
   plus its tests and docs) is one commit; only unrelated changes must
   be split. "and" in the title is fine when the parts serve the same
   purpose; it signals a split when they do not.
6. **No issue numbers in the title** — references belong in the body
   footer.

## Body Rules

1. **Optional by default** — most commits ship title-only. Write a body
   only when the change is non-obvious (the why is not inferable from
   title plus diff) or carries reviewer-relevant facts: trade-offs,
   compat or migration notes, perf numbers, known limits, follow-ups.
2. **Blank line after the title**, then wrap every line at 72.
3. **Why before what** — open with the motivation or the problem; the diff
   already shows how. Order: context, what changed at behavior level, why
   this approach over the alternatives, reviewer notes, footer
   (`Refs: #123`, `BREAKING CHANGE: ...`).
4. **Behavior, not narration** — describe what the code now does, not a
   file-by-file tour or pasted hunks.
5. **Concrete beats vague** — real numbers, error messages, and names
   ("cuts cold start from 340ms to 120ms"), not "improves performance".
6. **No filler** — no "this commit", no restating the title, no generic
   maintainability claims a reviewer cannot verify.

## Final Check

Before writing the commit, verify: the title alone tells a
`git log --oneline` reader what changed and why they care; the body —
when one is written — answers "why" for a reader six months from now;
unrelated changes are split out; no published history is being
rewritten. If the target commit is already pushed, print the improved
message and warn instead of amending.

## Example

```
fix: crash when config path is unset

load_config() assumed CONFIG_PATH is always in the environment and
raised KeyError before the logger is initialized, so the crash printed
no diagnostics. Fall back to the documented default path instead.

Alternative considered: exit with a clear error. The default matches
what the docs already promise, so no migration is needed.

Refs: #142
```
