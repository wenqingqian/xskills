# Better Commit Messages

Produce commit messages a reviewer can trust: a title a repo-only reader
can parse in a `git log --oneline` scan, and a body that carries the why.

## When to Use

- **On explicit invocation**: draft a message for staged/uncommitted work
  and commit; `--amend` rewrites the last commit's message (unpushed
  only); `<rev>` prints an improved message without touching history.
- **Skip**: throwaway WIP snapshots the user explicitly wants committed
  fast; merge commits and rebase artifacts generated by tooling.

## Workflow

```
1: gather   git status --porcelain; git diff --cached (fall back to
            git diff); git show <rev> for a rewrite; git log --oneline
            -10 to learn the repo's own type vocabulary
2: draft    title per Title Rules, body per Body Rules
3: check    run the Final Check below
4: apply    new commit via git commit with a heredoc message; amend only
            when the branch has no upstream or the commit is unpushed
            (git log @{u}..HEAD)
```

## Title Rules

The title is written for a **zero-context reader**: someone who knows the
repository (README, docs, code) but not this session, its review reports,
the PR thread, or the commit sequence. Every rule below serves that reader.

1. **Format is mandatory** — `<type>: <summary>`, or `<type>(<scope>): <summary>`
   when the repo's log uses scopes. The type prefix is never optional; a
   messy repo log is no license to drop it. Repo convention may adjust
   only which types are used and whether scopes appear. Types: `feat fix
   refactor docs test chore perf build ci style`.
2. **Imperative mood** — "add", not "added" or "adds". Lowercase summary,
   no trailing period.
3. **Length** — summary <=50 chars soft target, 72 hard limit.
4. **Specific and grounded** — name the actual change and its effect
   ("fix crash when config path is unset", not "fix bug"). Every word
   must be backed by the diff or the repo; references to artifacts
   outside the repo (review-finding IDs like "R1-R8", session shorthand
   like "review leftovers") are banned. Public issue numbers are the
   only allowed outside reference and live in the body footer.
5. **One outcome** — the summary is a single clause with a single head
   noun phrase; judge by grammar position, not by symbol:
   - No separator (`;` `+` `,` ` and `) may join two verb-bearing
     clauses — that is a two-purpose signal.
   - **Zero enumeration**: no comma or `+` list of parallel deliverables
     in the title, not even two items. Richness lives in the diff and
     the body, not in title commas.
   - Remediation, in order: rewrite to the umbrella outcome; if the
     parts are genuinely unrelated, title the dominant change and
     enumerate the rest in the body. **Never split an already-made
     commit** — advise a split only while drafting a commit that does
     not exist yet.
6. **No meta-narration** — the title states the change, not the commit's
   shape or sequence: file counts ("7 files"), "part 2/N", "pre-/post-*"
   markers are all banned.

## Body Rules

The body serves the same zero-context reader.

1. **Optional by default** — most commits ship title-only. Write a body
   only when the change is non-obvious (the why is not inferable from
   title plus diff) or carries reviewer-relevant facts: trade-offs,
   compat or migration notes, perf numbers, known limits, follow-ups.
2. **Blank line after the title**, then wrap every line at 72.
3. **Why before what** — open with the motivation or the problem; the diff
   already shows how. Order: context, what changed at behavior level, why
   this approach over the alternatives, reviewer notes, footer
   (`Refs: #123`, `BREAKING CHANGE: ...`). Footer refs must be public and
   look-up-able — never internal review numbering unless that numbering
   is committed in the repo.
4. **Behavior, not narration** — describe what the code now does, not a
   file-by-file tour or pasted hunks.
5. **Concrete beats vague** — real numbers, error messages, and names
   ("cuts cold start from 340ms to 120ms"), not "improves performance".
6. **No filler** — no "this commit", no restating the title, no generic
   maintainability claims a reviewer cannot verify.

## Final Check

Before writing the commit, verify: a repo-only reader can parse every
term in the title; the title names one outcome; the body — when one is
written — answers "why" for that reader six months from now; no
published history is being rewritten. If the target commit is already
pushed, print the improved message and warn instead of amending.

## Example

Title rewrite (enumeration -> umbrella):

```
- feat: score trio, count guard, trace collector, replay oracle
+ feat: offline verification for selection scores
```

Full message:

```
fix: crash when config path is unset

load_config() assumed CONFIG_PATH is always in the environment and
raised KeyError before the logger is initialized, so the crash printed
no diagnostics. Fall back to the documented default path instead.

Alternative considered: exit with a clear error. The default matches
what the docs already promise, so no migration is needed.

Refs: #142
```
